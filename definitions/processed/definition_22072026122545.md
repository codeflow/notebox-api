# Notebox — product brief (source, translated to English)

> Raw material provided by the human on 2026-07-22 for the `definitions` intake step.
> Originally written in Portuguese; translated to English (project language). The digest is `INTAKE.md`.

notebox-api is an API for a system called Notebox. The idea is that this system lets users store both
**annotations** (notes) and **task management**.

The system splits into 2 groups:

**Annotations**, where it is possible to store any kind of annotation. For annotations it is possible
to store an **annotation type**.

Example: I want to create an annotation type called RabbitMQ. In the type I can define fields that can
be used when I fill in the annotation.

The fields have the following composition:

* Icon (image of the annotation type's icon)
* Type (a list, with the options defined below)
* Field name (textbox)
* Visible for viewing (checkbox — this property indicates whether the field should be shown inside a
  datagrid or datatable. Example: if I have an annotation called RabbitMQ with the fields URL,
  Environment, Description, and the Description field does not have "Visible for viewing" checked, then
  in a datagrid or datatable only URL and Environment would appear.)

The type can be:

* Text (usually represented by a textbox) (Visible for viewing: true)
* List (usually represented by a combobox) (The list must have an option for whether I want to render
  the list items as **badges**, and the badge background colour can be chosen from a fixed palette of
  basic colours — red, green, blue, black, gray, yellow — and assigned to a badge item)
  (Visible for viewing: true)
* Number (usually represented by a textbox with a **slider**, ideal for choosing a value within a scale
  or range) (Visible for viewing: true)
* Free text (usually represented by a textarea) (Visible for viewing: false)
* Single choice (usually represented by a radio button; in this case it must be populated with the list
  items) (Visible for viewing: false)
* Multiple choice (usually represented by checkboxes; in this case it must be populated with the list
  items) (Visible for viewing: false)
* Image (Visible for viewing: false)

To illustrate registering an annotation:

An annotation type would be:

Annotation name: RabbitMQ

with the fields:

Icon: the RabbitMQ image (the system must ensure the image can be viewed at a small size to represent it
in datagrids and datatables)
URL: text field
Environment: can be a list, either just a combobox or as badges, with the items Dev, Hml and Prod
Description: a text field

The page has a left-hand sidebar menu where annotations and tasks are stored.
The menu displays like this:

Navigator
Annotations
    RabbitMQ (the created annotation type)
Tasks
    ....

In the menu, both annotations and tasks can be organized into **groups**:

Navigator
Annotations
   myGroup1
       RabbitMQ (the created annotation type)

Tasks
    myGroup2
        ....

So the system must allow creating a group for the items.

Clicking a menu item shows its details on the right-hand side of the page.
For annotations, opening one from the menu shows it in an **editable datagrid**, i.e.:

Example — the annotations of a type called RabbitMQ:

URL           | Environment |
https://...   | Prod.       | Here go Edit, Delete and Details
https://...   | Hml.        |
https://...   | Dev.        |

Edit, Delete and Details must be icons. Clicking Edit lets you edit inline in the datatable. Clicking
Edit opens the textbox or form control for each field of the type. Clicking Delete opens a dialog box
asking whether to delete the item, and Details opens a popup with all fields of the type — including
those marked Visible for viewing: false — plus Edit and Delete buttons inside the popup as well.

For tasks the structure is a little different:

Tasks can be linked to a group.
The structure of a task is:

Task | Start Date | End Date | Card | Priority | Status

The datatable that displays tasks must be editable to edit the fields above.
The Card column is a field that shows a Card code as an id (TST-3456) and a URL in case you want to point
to the card's URL. But the datatable column must display only the id, clickable to the card's URL.

The datatable must be a datatable with a **collapsible sub-datatable** to display subtasks.

A subtask must have:
Task | Start Date | End Date | Card (a subtask may or may not have a card) | a checkbox to mark the task
as done. When a subtask is completed (checkbox checked), the progress bar of the task's status field is
updated. The task's status percentage must be based on the number of subtasks, and as I add a subtask it
updates the task's progress bar.

The task's start date and end date must consider the start date of the first subtask and the end date of
the last subtask.

In addition, the task list allows adding a **details** field that is not shown in the tasks datatable.
There must be only an icon to display the details.

The task's details field is a free field with a rich-text editor (WYSIWYG) that allows adding font
styles, colour, underline, bold, and inserting images. Clicking the details icon in the datatable must
show that task's details in a popup that renders the rich-text editor with the formatted text.
